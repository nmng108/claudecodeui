# SSH key for git

## Requirements

1. A place in Settings to see the public SSH key git uses for `git@host:...` and `ssh://`
   remotes, so the user can copy it into GitHub, GitLab, Bitbucket or any other git server.
2. When no key exists the app does not create one by itself. The user clicks *Generate SSH
   key*.
3. In Docker the key survives container recreation, and the user can mount their own key
   instead.
4. The private key is never sent to the browser, logged, or stored by the app outside the key
   file.
5. In Docker, the AI agents running in the app container can use the key to sign in to git
   servers but cannot read it, delete it, or add keys of their own to the agent.

## Two ways to hold the key

| | Native | ssh-agent sidecar (Docker compose) |
|---|---|---|
| Used when | `CLOUDCLI_SSH_CONTROL_SOCKET` is not set (running the package directly) | The compose files set it |
| Private key lives | In `~/.ssh` (or `CLOUDCLI_SSH_DIR`) of the user running the app | In a separate container, never mounted into the app container |
| Who can read it | Everything running as that user | Only the sidecar |
| Who can use it | Everything running as that user | Processes in the app container, for signing only |
| Replace from the UI | Yes, for a key the app generated | No: `rotate-key` on the host |

Both sit behind one interface, so the routes and the UI are the same.

## Design

### Provider interface

`server/modules/ssh-keys/ssh-key-provider.ts` defines `SshKeyProvider`:

```ts
getKey(): Promise<SshKeyInfo>
generateKey({ replace? }): Promise<SshKeyInfo>
```

`SshKeyInfo` carries the status (`present`, `missing`, `unreadable`), origin (`generated` or
`existing`), algorithm, one-line public key, `SHA256:` fingerprint, comment, a display
location, `canGenerate` / `canReplace` / `reason`, and `provider` (`native` or `agent`). It
never contains the private key.

### Key logic (`ssh-key-core.ts`)

One dependency-free file used by both providers and by the sidecar (it is copied into that
image and run by Node's built-in TypeScript support, so it uses only erasable syntax and
Node built-ins).

- The directory is the one given (`~/.ssh`, `CLOUDCLI_SSH_DIR`, or `/keys` in the sidecar).
- It looks for `id_ed25519`, `id_ecdsa`, `id_rsa` in that order and reports the first it finds.
- The public key comes from the `.pub` file. If there is none, `ssh-keygen -y -P ""` derives
  it; the empty passphrase makes a protected key fail instead of prompting, and the key is
  reported as `unreadable`.
- The fingerprint is computed in-process (SHA-256 of the key blob, base64 without padding), the
  form git servers display.
- **Generating** runs `ssh-keygen -t ed25519 -N ""` with the comment `cloudcli@<hostname>`.
  The pair is created under a temporary name in the same directory and renamed into place, so
  a failure never leaves a half-written key. The directory is created `0700`, the private key
  is `0600`. One generation runs at a time; a concurrent request gets `409 SSH_KEY_EXISTS`.
- **Existing keys are read, never changed.** `generate` over an existing key is `409
  SSH_KEY_EXISTS`. `replace: true` is honoured only for `id_ed25519` whose comment starts with
  `cloudcli@` (a key this app generated); any other key gets `403 SSH_KEY_NOT_REPLACEABLE`.
- A directory that is not writable is reported (`reason: "read-only"`, `canGenerate:
  false`). A missing `ssh-keygen` is `501 SSH_KEYGEN_MISSING`.

### API

Mounted at `/api/ssh-keys` behind the normal authentication.

| Request | Result |
|---|---|
| `GET /api/ssh-keys` | `SshKeyInfo` |
| `POST /api/ssh-keys/generate` with `{ "replace": false }` | The new `SshKeyInfo`, or 409 / 403 / 501 as above. `replace` must be a boolean. |

### UI

Settings > Git has an *SSH key* section (`SshKeySection`):

- no key: an explanation and a *Generate SSH key* button (hidden when the directory is
  read-only, with the reason shown instead);
- key present: type, fingerprint, location, origin, the public key in a read-only box with a
  *Copy* button, and links to the "add an SSH key" page of GitHub, GitLab and Bitbucket;
- a key generated by the native provider also has *Replace key*, which asks for confirmation;
  with the sidecar the page shows the `rotate-key` command instead;
- a key that is not readable (for example protected by a passphrase) is explained, not shown;
- a standing note on who can use the key, worded for the provider in use.

## The ssh-agent sidecar

```
 app container (agent user, AI agents)              ssh-agent container
 ┌──────────────────────────────────┐              ┌───────────────────────────────────┐
 │ SSH_AUTH_SOCK=/run/ssh/agent.sock│──ssh-run vol─▶ filtering proxy ─▶ ssh-agent       │
 │ server ──/run/ssh/control.sock───│──────────────▶ control API (public key, generate) │
 │ no key files                     │              │ /keys (ssh-keys volume): the key   │
 └──────────────────────────────────┘              └───────────────────────────────────┘
```

### Why a proxy

`ssh-agent` only accepts connections from its own user and offers every client the full
protocol: list, sign, but also remove identities and load others. The service therefore runs
the real agent on a private socket (`/tmp/ssh-agent.sock`, inside the sidecar) and exposes
`/run/ssh/agent.sock` through `ssh-agent-proxy.ts`. The proxy parses the agent protocol and
forwards only `SSH_AGENTC_REQUEST_IDENTITIES` (list public keys) and
`SSH_AGENTC_SIGN_REQUEST` (sign). Every other request, including `ssh-add -D`, adding a key,
locking and extensions, is answered with `SSH_AGENT_FAILURE` and never reaches the agent.
Requests are handled one at a time so answers stay in order; a zero-length or over-256 KiB
message closes the connection.

### Control API

Served on `/run/ssh/control.sock` (HTTP over a unix socket):

| Request | Result |
|---|---|
| `GET /health` | `200` once the service is up (the container healthcheck) |
| `GET /key` | `SshKeyInfo` with `provider: "agent"` and `canReplace: false` |
| `POST /generate` | Creates a key when none exists and loads it into the agent. `replace: true` is refused (`403 SSH_KEY_REPLACE_DISABLED`). |

There is no way to read, import, delete or replace a key through it, because the agents next
to the app can reach the same socket. Rotating a generated key is done on the host:

```sh
docker compose exec ssh-agent rotate-key        # dev stack: dev-ssh-agent
```

It prints the new public key; add it to your git servers and remove the old one.

### The container

- Debian, same as the app images. Starts as root only to `chown` the two volumes, then
  `setpriv` drops to uid 10001 with every capability removed.
- `network_mode: none`, read-only root filesystem, `cap_drop: ALL` plus `CHOWN FOWNER KILL
  SETUID SETGID`, `no-new-privileges`. It needs no network: everything goes through the
  `ssh-run` volume.
- Volumes: `ssh-keys` on `/keys` (only this container), `ssh-run` on `/run/ssh` (both).
  `dev-ssh-keys` / `dev-ssh-run` in the dev stack.
- The sockets belong to group `AGENT_GID`, the group of the app's `agent` user, mode `0660`.
  Build both images with the same `AGENT_GID`.
- A watchdog re-loads the key into the agent if the agent ever loses it. Restarting the
  container loads the key from `/keys` again.
- A key of your own can be mounted read-only into `/keys` (see the compose files). It is
  shown but never replaced. Passphrase-protected keys cannot be loaded unattended.

### In the app container

- `SSH_AUTH_SOCK=/run/ssh/agent.sock`, and `IdentityAgent /run/ssh/agent.sock` in
  `/etc/ssh/ssh_config.d/50-cloudcli.conf`, so `ssh` and `git` use it even from processes
  that start with a cleaned environment.
- `StrictHostKeyChecking accept-new`: a new server's host key is recorded on first contact
  and refused if it later changes. `known_hosts` is `~/.cloudcli/known_hosts` (the
  `cloudcli-home` volume), so it survives recreation.
- `CLOUDCLI_SSH_CONTROL_SOCKET=/run/ssh/control.sock` makes the server use the sidecar.
- `depends_on: service_healthy` starts the app after the sidecar is ready.

## Security notes

- In the sidecar setup the app container holds no private key. A process there can ask the
  agent for the public keys and for signatures; it cannot read the key, remove it, replace
  it, or load another into the agent. Tested: `ssh-add -D` is refused, `ssh-keygen -Y sign -U`
  works, and no key file exists anywhere in the app container.
- **It can still use the key.** An agent that is told (or tricked) to run `git push` pushes
  as you, to everything the key can reach. Use a dedicated key with limited access, such as a
  deploy key per repository, rather than a personal one. Asking for approval on each use
  (`ssh-add -c`) is a possible later addition.
- The control socket and the agent socket are reachable by every process in the app
  container (group access). The control API can only show the public key or create a key
  when none exists.
- The key is not encrypted at rest and has no passphrase: it must work unattended. Volume
  and file permissions are the protection. Anyone who can read the `ssh-keys` volume (for
  example with root on the Docker host) has the key.
- Native mode (no sidecar) offers none of this: everything running as the same user can read
  the private key. The page says so.
